# Activity history

Open **Activity history** in the project rail, or **History** in the conversation's live Activity disclosure. The latter starts with the owning project selected. The history opens on the newest available events, with project and event-type filters, **Load older events**, and **Refresh**. Live Activity and toast delivery are unchanged; opening the history never replays a toast.

## Producer coverage

| Producer                            | What history records                                                                                                                                                                                                                                                          |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `notifications.send`                | Accepted notification title, body, level, and source. Recorded before the toast debounce and independent of OS delivery; multiple accepted requests remain distinct.                                                                                                          |
| Native `ClientEvents` notifications | Shortcut, screen capture shortcut, and clipboard failures, including sends to a window with no subscriber. Drop-down accessibility warnings and available app versions are captured directly at their source.                                                                 |
| Provider authentication             | The same generic direction to Settings as the session toast. No sign-in URLs, codes, SDK notices, or tokens.                                                                                                                                                                  |
| Agent-action notices                | Successful mutations that already warrant receipts, including renderer-owned receipts. Routine tool calls are not logged.                                                                                                                                                     |
| Project Sessions                    | First durable Pi session creation, fork creation, and committed resolution. A family resolution is one event for the root, not one per member. Draft identities without a transcript are not creation events.                                                                 |
| Managed Worktrees                   | Confirmed Git landing, manual or automatic, before resolution or checkout cleanup. Auto-merge recovery can also record a confirmed matching receipt. Resolution remains a separate event, including when no merge happened.                                                   |
| Prompt automations                  | One row per retained occurrence: manual, scheduled, or matching event trigger; queued, skipped, blocked, canceled, running, completed, or failed disposition. Reasons and links use the existing occurrence, run, and rule records; authority lives in the automation ledger. |
| Widget schedules                    | Attempted handlers and their outcomes, with a link to the widget. They share the global artifact runtime, so a run does not infer a project from whichever window happened to show the widget.                                                                                |
| Auto-merge workflow                 | Started attempts and terminal outcomes handled by the worker, with the available reason and session link. Nonterminal eligibility/waiting reasons remain in the live Auto-merge surface; they do not produce an event on every recheck.                                       |

## Persistence and limits

Cake stores history metadata under its backend state directory in `activity.sqlite`. Stable producer IDs (e.g. worktree operation IDs, renderer control request IDs, and session creation IDs) deduplicate inserts across windows and restarts. Native notices with no durable source identity are distinct emissions. Prompt automation history is read from the existing durable ledger and does not copy task prompts or trigger message bodies. That row shows the latest outcome of the occurrence, not a sequence of interim queue states. Use Refresh to see updates while the dialog is open.

The journal is best-effort: a failed write does not affect delivery or the underlying workflow. It is not a transaction log for Git or Pi. A crash between a lifecycle commit and its history write can leave a gap; auto-merge has matching Git receipt recovery, but older events and manual Git outside Cake are not backfilled. Disabled or unmatched rules, dormant widget schedules, and routine polling/condition checks do not create entries. Notifications that require renderer control are only recorded once the existing renderer control accepts them; this does not grant headless notification permissions.

Window-local bootstrap/transport failures and immediate command feedback (e.g. draft move/undo, editor opens, render/observer retries, or failure to deliver a native notification) stay in their existing toast or error surfaces. Discussion and automation session lifecycle, scheduled-message delivery receipts, and external PR completion keep their existing status surfaces. No transcript, UI snapshot, or retry callback is stored in the feed. Removed projects or other unavailable destinations may no longer open; history stays visible.
