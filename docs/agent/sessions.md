## Batched delivery

Everything that waits instead of waking the parent—notification-mode results, passive FYIs, routine Workboard posts and quiet worker reports—accumulates in one pending batch per conversation (global Cake Chat, a Project Chat or a parent Project Session). The first item starts that conversation's timer. If the user sends a message first, the whole batch rides along with it and the timer is cancelled. Otherwise Cake delivers the whole batch as one turn 5 minutes after the first item or, when sooner, shortly before the conversation's prompt cache is estimated to expire (the estimate sessions.list shows); an unknown or expired cache uses the 5-minute window. A batch turn has no user message: handle everything together and reply once, continuing only already-authorized work. It never steers or runs beside active work—a busy conversation receives the batch after its current work, including items that arrived meanwhile—and an explicitly stopped conversation or one awaiting interrupted-work review waits for the user's next message. Reply mode, direct questions and blockers stay immediate. Timers and admissions are durable and deduplicated across restart.

Passive FYIs are durably retained as typed agent-authored context in the batch, not fake user messages or raw reminder markup. They do not interrupt active work. Delivery is deduplicated by durable notice and input IDs across restart; canceled inputs do not rearm notices. Existing explicit result/continuation choices are preserved, not silently migrated. Installed prompts/tools update with the next application deployment; already admitted inputs cannot be retroactively un-sent.

Delegated launches and follow-ups are asynchronous. Expecting results never implies waiting; blocking run/parallel/wait requires the user’s explicit request. Launch intent is separate from report presentation and response obligation. For `subagents.start`, choose `continuation: "none"` when only a result/report is needed, or `"resume"` when the parent must inspect it and continue dependent work or explain failure. Both owe a result; a linked result never cancels resume. Subagents default to none, follow-ups inherit unless overridden, and blocking run/parallel/wait return directly without an extra continuation. `message_parent` blockers/questions stay immediate. Session launch/send uses resultDelivery, not private-worker continuation. Active parents receive results through their normal serial queue, never steering or concurrent turns. Workboard-only children may select resultDelivery: "ignore"; all posts use default explicit-audience/root delivery; completion grants are replaced rather than layered into a second wakeup. Independent `session.create` from a Project Session now retains a quiet initial completion for that creator by default; local user/UI creation without a creator owes nothing.

Quiet private-worker reports and passive references remain in `sessions.reports` until explicitly handled, independently of Pi input admission.
