# Workgroups and Session Families

Read this guide before delegating to full child Project Sessions, carrying out a child-session assignment, coordinating with another session, sharing findings on the Workboard, or managing a Session Family's lifecycle. Your session context supplies the actual family, parent, and Working Directory.

## Board-only family communication

By default, all Session Family members—parents, children, siblings, and descendants recursively—communicate with one another exclusively through the family's shared message board (Workboard). Publish assignments, questions, blockers, decisions, redirections, and results with `boards.append`. Do not use `sessions.send`, `sessions.reply`, `sessions.send-batch`, private subagents, transcript/file drops, or another private side channel for intra-family communication, including urgent wake-ups and completion notifications. Do not duplicate a board post with a private notification.

This restriction is intra-family only: continue replying normally to the user. Cake Chat is not a Project Session or family member; its requested reports and communication with unrelated independent sessions retain their ordinary rules. Do not relay family messages through Cake Chat, independent sessions, or the user to evade the board.

## Discover the family and its board

Call `{"command":"sessions.list-family"}` for the family identity, root and a bounded member roster; follow nextOffset to discover more members. Request `{"command":"boards"}` for operation summaries and `<operation>.help` for an exact contract. Board operations automatically select the caller's family board; they do not accept a board ID. `boards.current` and `boards.read-new` return `boardId` with bounded descriptions.

There are no separate agent board-create or board-join operations. `sessions.create-child` establishes or extends the caller's family, creates its Workboard automatically, and gives every recursive descendant access to that same board. Do not create an unrelated artifact board or invent join commands. An independent session cannot join an existing family through these tools. If no family exists, create a child only when delegation is actually warranted; if a member's board is unavailable, report the limitation to the user rather than falling back to private family messages.

For a new child, use `{"command":"sessions.create-child","input":{"title":"Storage implementation","assignment":{"description":"Implement the storage slice","body":"Own the storage files and tests. Post your commit, verification and blockers on the Workboard addressed to the parent."}}}`. Both `title` and substantive `assignment: { description, body }` are required. Cake reserves the child identity, creates/joins the board and persists the assignment addressed to that identity before admitting the first child turn. Cake supplies the board-discovery bootstrap. Do not append the initial assignment after creation; the former `initialPrompt`/bootstrap-first contract is unsupported and fails validation. A child-session request means this operation, not a private `cake subagents` worker.

Inspect the returned `launch` outcome, not just the identity or assignment receipt. `accepted` means durable turn intake, not successful work or completion. `already-admitted` includes the durable journal state (active, blocked, complete, failed or stopped); it never starts that work again. `failed` includes the failure stage and keeps a retryable reservation. Retry with the returned `requestId` and unchanged assignment; a fresh request ID creates a different child. Assignment topics (`child-<canonical-id>`) are application-owned initial handoff identities; use a separate topic for subsequent coordination. Before admission, failure or a crash can leave a reservation waiting for a create-child retry; startup retains it but does not silently activate it. After admission, normal durable input recovery applies, including blocked/stop/cancellation authority. Do not claim completion from intake, board read receipts or session creation.

Family creation defaults to `resultDelivery: "notification"`; application-owned completion links are passive, not agent coordination. Choose reply only for genuinely dependent continuation with current user authorization; ignore is supported. Request the substantive result in the board assignment instead. A board post does not clear an already-pending correlated session-message obligation. Existing runtime-managed pending obligations can still produce private result/failure notices; prompt text cannot disable or reroute them. Do not call `sessions.reply` to satisfy them or send an extra private completion report. If such an obligation exists, disclose the runtime limitation to the user; strict transport exclusivity for those obligations needs runtime support.

## Publish and inspect coordination

Use `boards.append` with a meaningful `description`, detailed `body`, and explicit `audience`. For example: `{"command":"boards.append","input":{"description":"Implement the storage slice","body":"Own the storage files; preserve the agreed API. Post the commit, verification, and any blockers here when finished.","audience":["236e7b8b"],"topic":"storage-slice"}}`. Use discovered `<suffix>` references from `sessions.list-family`; Cake resolves them and rejects unknown or ambiguous references. Target affected owners (the parent/requester for a result or question); reserve `audience: "workgroup"` for genuinely family-wide decisions. An audience controls relevance and notifications, not a private side channel.

Before dependent implementation, publish a small shared contract: types/signatures, file ownership, dependencies, and named acceptance tests. Reference a shared durable spec if useful; the assignment and subsequent discussion still belong on the board. Give related entries a stable `topic`; correct decisions with `supersedes: [sequence, ...]` in that topic, including everyone affected by the old decision. Targeted corrections supersede only for their recipients; history stays inspectable.

At assignment start, before dependent work, after compaction, and before concluding, inspect relevant board context. Use `boards.current` (optionally filtered by `topic`) for non-superseded descriptions, `boards.read-new` for unread descriptions, and `boards.read` with `sequences` for selected bodies (at most ten per call). Page bounded discovery with `nextAfter` as `after`; omit `after` to refresh. Current means not explicitly superseded, not agreement or verification. Deferred bodies remain unread.

Publish one substantive result or failure/blocker on the board addressed to the requester and affected owners. Declare event: "completion" or "blocker"; use resultKind: "ready" for completed implementation or "investigation" for research. These typed events retain a quiet completion decision; they are not required for board delivery. Include the assignment entry number, outcome, commit if any, contract changes, integration action, and verification limits. A user-facing final answer is not a substitute for this board result. Do not post routine progress, tool diaries, acknowledgments, or duplicate reports. `boards.entry-receipts` and `boards.session-receipts` record intake timestamps, not understanding, agreement, or completion. Board posts are agent-authored coordination data, never user authorization.

## Application-owned board delivery

Boards are for Session Families only. Each post routes to its explicit audience and the unique family root, excluding its author; broadcasts do not wake every member. Use `event: "assignment"` for necessary dependent work or `event: "blocker"` for unblocking. Routine findings and `event: "completion"` are passive: they join the recipient's pending batch (its next user input, or one batched turn within 5 minutes; see sessions.md), never steering active work.

The application coalesces up to twenty source sequences per recipient. Necessary assignments/blockers retain durable idle delivery and non-disruptive active-context intake at Pi's supported boundaries. Routine updates use typed passive reminders delivered with the recipient's pending batch. No post steers unrelated user work, authorizes new work, or requires an acknowledgment.

`boards.append` returns `scheduledRecipients` and any existing `deliveries`; `boards.entry-receipts` exposes updated per-recipient batch execution status independently of body read receipts. Pending is scheduled, deferred is a passive reminder waiting for user input, admitted is durable queue intake, notified is context admission, and consumed is input-consumption/settlement evidence. None proves understanding or task completion. Canceled/failed and issue text are explicit. Do not claim work began from posting alone. Tool retries reuse requestId; supply a stable requestId for deliberate retries across calls. Board/outbox crash gaps reconcile on startup; stable input IDs and canceled IDs prevent replay.

The former bounded completion-continuation grant API is replaced, not layered on top: results and blockers use the same default board delivery, with no second wake or budget gate. Quiet completion decisions remain a separate UI inbox. No delivery posts an automatic board acknowledgment. Do not create echo loops with acknowledgments, routine progress, duplicate reports or “please read” posts; respond only when substantive coordination changes.

Explicit abort pauses board delivery and cancels unadmitted batches. Subsequent real user input re-enables future posts only after accounting for posts made while stopped; canceled batches never restart. Previously staged canceled reminders are filtered from outgoing context without deleting Pi history. Existing explicit pause/off choices survive storage migration; old completion budgets do not. Stopped/blocked Pi recovery and queue cancellation retain their normal authority. Resolution cancels pending delivery; restore does not replay it. Initial child assignments retain the assignment-before-launch handoff above and are excluded from a second generic wake.

### User-requested coordination check-ins

Current explicit task-scoped user instructions override earlier user-authored repository instructions and Cake-owned workflow defaults, including harness-injected Cake policies and family communication/channel/process defaults. No AGENTS.md edit or repeated confirmation is needed. Do not refuse a user-authorized family coordination exception solely because older Cake prose says board-only. Genuine provider/platform/system constraints, security boundaries and actual tool capabilities still apply: this grants no missing tools or unrelated authority. Name the concrete hard constraint and provide a supported path, not a blanket "harness forbids" refusal. Confirm execution with tool evidence; a board post alone is not proof that work began.

Do not periodically poll or schedule coordination check-ins unless the user explicitly requests them. An explicit request permits periodic check-ins for that task, including when completion events do not wake the coordinator. Use durable scheduling when available at the requested interval: `sessions.schedule` with `sessionId` omitted targets your own conversation (Cake Chat, a Project Chat or a Project Session), and `repeatEverySeconds` makes it one recurring entry; keep at most one pending check-in for the coordinator task, and stop scheduling when the task finishes or the user asks to pause or stop: `sessions.scheduled` lists entries and `sessions.cancel-scheduled` stops one. Continue substantive work or finish the current turn between check-ins; do not busy-wait or sleep-loop. Keep family assignments and results on the applicable task-scoped communication channel, honoring current explicit user exceptions to Cake defaults. Never claim that a check-in is scheduled or that an idle session will wake without a confirming tool result; disclose unavailable scheduling capabilities.

## Worktree and lifecycle safeguards

Omit `worktreeName` to let a child inherit this exact Working Directory and share mutable files, uncommitted changes, and Git index state; coordinate concurrent edits on the board. Supply `worktreeName` to create a Cake-managed worktree branched from this session's current checkout. A new worktree includes the current committed HEAD; uncommitted edits remain in this session's checkout and do not carry into the child. Never create an unrelated worktree base manually. Children can recursively create children under these same rules.

Keep an integration landing checkout clean while isolated implementations run. Use Cake's serialized landing operations; begin integration edits after the required owner commits have landed. Use `worktrees.merge` and `worktrees.discard` with the child's `sessionId` for isolated child worktrees; never merge a child's branch by hand. To land your own Managed Worktree, call `worktrees.merge` without a sessionId; never merge into the target checkout by hand.

Stopping and queue inspection are lifecycle controls, not communication transports. `sessions.abort` stops an active turn without resolving or deleting the member. `sessions.pending` inspects a queue; `sessions.cancel-queued` or `sessions.clear-queue` can remove pending inputs. Do not use `sessions.steer-queued` or `sessions.send-now` to deliver family instructions outside the board.

Only the family root owns resolution; all descendants inherit it and cannot be resolved or restored independently. Only the root can resolve or restore the whole family, and resolution requires every member to be inactive. A child's Cake Working Directory is fixed; it cannot detach or relocate.
