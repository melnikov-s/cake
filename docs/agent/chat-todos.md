# Chat to-dos

Read before starting an unsettled request, reviewing a report, or changing/reconciling to-dos in Project Chat or global Cake Chat.

Project Chat and global Cake Chat (not coding sessions) have `todos.list`, `todos.read`, `todos.create`, `todos.update`, and `todos.update-many`, the injected to-do baseline, and the To-do pane. A Project Chat edits its project's list. Global Cake Chat has its own separate list, whose session, subagent and source links may target any registered project.

**Every user request that isn't fully settled in the same reply gets a to-do, created before or as the work starts.** This includes delegated work of any kind (subagents, background lookups, sessions), brainstorms and open-ended discussions, and anything phrased as "look into", "find out", "research" or "come back to me". The only exceptions are quick factual answers fully given inline and casual conversation. A follow-up on an existing topic updates that item instead of creating a new one. Each actual new Project Session automatically receives one linked to-do at creation (including child sessions and forks) in its project's list, and sessions that global Cake Chat creates also get one in Cake Chat's list; read/update that item rather than duplicating it. Never bulk-import history.

**Closing to-dos.** Close a to-do yourself when the work is actually done: the change merged or shipped, the requested operation finished and was checked, or the user said they're satisfied with the outcome. Research, investigations, brainstorms and lookups stay open after the report arrives. Set the status to "Report delivered; awaiting your review", link the report, and close the to-do only after the user has read it and either said they're satisfied or moved on without follow-ups. Closing automatically when the linked session is resolved still applies.

**When a to-do is associated with a session, resolving that session completes the to-do automatically; don't mark it done by hand.** So for a session-linked item, "close it" means resolving the session; you close every other item (subagent-only, discussion or source-only items) yourself by the rule above. The injected to-do baseline lists each open item's linked session IDs in `sessions`, so you can tell which items `sessions.resolve` will close. After resolving, update only the title, description or status if needed. `state: "done"` on an already-done item is a no-op for the state: alone it commits nothing, and other edits in the same update still apply, even when the only change since your revision was that automatic completion. The receipt's `note` says why the item was already done. Any other change since your revision is still a conflict that names what happened; reread and re-apply.

Titles identify tasks; descriptions give the latest update, not a task restatement. Use one or two short sentences. Emphasize the user-relevant outcome, current state and remaining blockers or decisions. Omit commit hashes, commit messages and routine implementation/test bookkeeping; keep technical provenance in linked reports or code references. Retain verification gaps or failures that affect readiness. Update when meaningful progress, findings, completion, review/merge readiness or blockers change, using available events and evidence. Say when no findings or fix exist; never claim finished, merged or fixed without evidence. Do not poll, schedule timers or wake workers merely for status; preserve notification behavior.

Examples:

- "Preset prompts are implemented. Review and merge still pending."
- "Apple Silicon packaging is implemented. Review, merge and release remain pending; downloaded-app first launch and release CI are unverified."
- "Startup delays first display, but the full ~500 ms remains unexplained. No fix implemented."
- "Live widget-theme fix is underway, including System mode. No findings reported yet."

The required `description` carries this update even when optional freeform `status` is used; status is not lifecycle. Items have only open/done lifecycle. Open items never authorize polling or wakes.

Attach a few high-value, descriptively titled links when available and relevant: an existing PR/MR as the primary review destination for PR-based work; an issue/ticket for requirements or discussion; a usable preview, deployment or artifact to inspect the outcome; the exact useful report or code change/commit, especially for no-PR local merge workflows such as Cake; and the associated Cake session. Omit irrelevant or redundant links; never invent a PR/MR or create one merely to populate a to-do. Update links as work evolves, including adding a PR/MR once created. For investigation/research to-dos, attach or update a kind=source link with a descriptive title such as 'Investigation findings' to the exact original findings message when the application's retained result-message ref becomes available (completion/report metadata or messages.list). Use that exact ref; never invent message IDs or substitute a session-only link, a summary, or a moving ?message=last destination. Keep the original report reachable from the to-do even when another conversation topic defers its notification or summary. Do not copy reports into artifacts, request extra report wakeups or change delivery/completion/lifecycle semantics just to attach a link. Use kind=subagent with its public handleId and parentSessionId to link a private worker, never its private Pi session ID. Subagent links open its existing chat/report. Subagents have no resolve lifecycle: completion, error, abort or release never automatically closes a to-do; subagent-only items require explicit done. Mixed items retain the existing all-Project-Sessions-resolved closure rule. Session associations are required work (lifecycle); source links are context only and never affect automatic completion. Preserve required session associations and existing subagent associations when updating links; association updates replace the complete list.

`associations` accepts titled `session` links (canonical identities or discovered suffixes), `subagent` links (`parentSessionId`, public UUID `handleId`, `title`), and `source` links to exact messages/reports, subagent chats/reports, attachments, artifacts, web URLs or workspace files. Omit optional source links if nothing useful exists; do not remove required session associations. A Project Chat's targets must belong to its project; global Cake Chat's targets may belong to any registered project. Parent/session suffixes are stored canonically. New subagent associations validate the retained public worker record and its parent. A subagent link uses `cake://subagent/<encoded-parent>/<handle>` to inspect its existing chat/report, including saved history after release; it is never a `cake://session/<private-Pi-ID>` link. If worker metadata has already been released, link the exact retained report message in the parent instead.

Default `todos.list` returns bounded title/id/state/revision rows only, filtered by state/query with offset/limit (default 20, max 50). For reconciliation use **one** `todos.list` with `state: "open", view: "reconciliation"`, which joins canonical work session IDs to authoritative effective resolved booleans (`null` plus reason for unknown), then **one** `todos.update-many` with `expectedRevision` for each edit. The bounded batch is atomic: any conflict commits nothing and names the conflicting identity/current revision. Receipts follow input order and include only new revisions, canonicalization or unexpected changes; create also returns its new ID. `detail: true` opts into content on create/update; `todos.read` is exact detail by ID. No per-session inspection or transcript reads are needed for reconciliation.

Resolving all associated Project Sessions automatically completes a linked open to-do in any list (the session's project list and global Cake Chat's list), whether resolution comes from the UI or a tool. This also applies when a link is added after resolution and to historical open items reconciled on application startup. Only actual session associations are required work: source/report links neither veto completion nor complete source-only discussion items. Restoring sessions never reopens a to-do. Marking a to-do done never resolves, merges, deletes or stops its associated work. Report delivery is not resolution. Read before updating, pass `expectedRevision`, and preserve explicit user decisions after conflicts.

The To-do toolbar button uses the shared resizable side pane. The latest result message (worker report, session reply or completion notice) linked to a to-do also shows a Done checkbox that mirrors the list item live, whoever changed it; toggling it is the same user done/reopen as the pane. Selection only supplies context to the next user input; it never sends or wakes. User selection/deselection, done/reopen (from the pane or a result message), and confirmed session resolve/restore changes persist until consumed with a user message; global Cake Chat hears session changes only for sessions its list links. Historical reminders can be stale: read/list for exact current state. A bounded current baseline accompanies fresh/reset context; unchanged turns do not append repeated selection reminders.
